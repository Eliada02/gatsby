# Architecture

Where things live and how data moves. The reasoning behind these choices is in
[docs/architecture.md](../docs/architecture.md); this file is the map.

---

## Application

Gatsby 5 with React 18, TypeScript in `strict` mode. Every route is statically
generated at build time; there is no server-side rendering at request time and
no client-only route.

Routing is file-based: a file in `src/pages/` is a route. The one exception is
resource detail, generated by `createPages` in `gatsby-node.ts` from
`src/templates/ResourceDetail.tsx` — one static page per resource.

`trailingSlash` is Gatsby's default (`always`), so `/about/` is the canonical
form of `/about`. The SEO layer normalises to it.

The four Gatsby lifecycle files each own one thing:

| File                 | Owns                                                                                          |
| -------------------- | --------------------------------------------------------------------------------------------- |
| `gatsby-config.ts`   | siteMetadata (the SEO layer's source of truth) and plugins                                    |
| `gatsby-node.ts`     | The `@/` webpack alias, page generation, and build artefacts (robots.txt, social card, icons) |
| `gatsby-ssr.tsx`     | `<html lang>`, site icons, the dataLayer stub, and GTM when configured                        |
| `gatsby-browser.tsx` | Global CSS imports and the `page_view` event on route change                                  |

## Components

Four layers, and the layer decides what a component may do:

```
primitives/   Button, ButtonLink, Container, Section, VisuallyHidden
              Render real elements. No content, no data, no side effects.

patterns/     Badge, SectionHeader, PageHero, PointsList
              Compose primitives into repeated shapes. Still content-free.

sections/     Hero, PatientJourney, PlatformOverview, ImpactCalculator,
              SecurityPreview, TrustBar, FinalCta, AboutStory
              A band of a page. Takes its content as props — never imports it.

layout/       Header, Footer, MobileNav, SkipLink, ConsentBanner, Layout
              Page chrome. Landmarks are fixed here so no page can get them wrong.
```

Feature components (`resources/`, `contact/`, `seo/`) sit alongside these and may
hold state and talk to the API.

**Sections never read content.** Pages read from `src/lib/content/source.ts` and
pass it down. That is what keeps sections reusable and testable with fixtures.

## Content

```
content/*.json  →  src/lib/content/source.ts  →  pages, API handlers, gatsby-node
```

`source.ts` is the only module that imports from `content/`. Swapping the JSON
for a CMS means rewriting that one module. Everything else consumes its exports.

Types live in `src/types/content.ts` (editorial catalogue) and
`src/types/site.ts` (page copy). The JSON is cast rather than validated at
runtime; `source.test.ts` asserts the invariants a CMS would enforce on publish
— unique slugs, known enum values, resolvable references, no certification
claims.

## API

Two Gatsby Functions in `src/api/`, deployed with the site:

| Endpoint             | Does                                                                           |
| -------------------- | ------------------------------------------------------------------------------ |
| `GET /api/resources` | Filters, sorts and paginates the library server-side; returns one page         |
| `POST /api/contact`  | Validates a submission and answers `202`. It delivers nothing and logs nothing |

Both import types from `src/types/api.ts`, which the browser client also
imports, so a change to a response shape breaks compilation on both sides.

**Functions use relative imports, not `@/`.** Gatsby compiles them through a
separate pipeline where the alias is not guaranteed to apply.

The client half lives in `src/lib/api/`: `client.ts` (one `fetch` wrapper owning
timeouts and `ApiError`), `resources.ts` and `contact.ts` (per-endpoint calls).

## State and data flow

There is no state management library, and no application-level context.

- **Filter state is the URL.** `?search=&category=&sort=&page=` is parsed by
  `src/lib/resources/query-params.ts` into a query, the query is fetched, the
  response is rendered. Changing a control writes a new URL and the cycle
  repeats. Nothing keeps a second copy.
- **Server data** lives in `useResources`, which holds a discriminated union:
  `idle | loading | success | error`. Illegal states are unrepresentable, and
  the empty state cannot be forgotten because the compiler requires the branch.
  In-flight requests are aborted when the query changes.
- **UI state** is local `useState` — menu open, form values, consent choice.

## Analytics

```
component → named helper (lib/analytics/track.ts)
          → trackEvent (lib/analytics/dataLayer.ts)   ← the consent gate
          → window.dataLayer                          → GTM, if configured
```

- `src/types/analytics.ts` is the tracking plan as a discriminated union. An
  unknown event name or a missing parameter is a compile error.
- `lib/analytics/consent.ts` defaults to **denied**. Events attempted before a
  choice are queued (bounded at 20) and flushed only if consent is granted.
- No component touches `window.dataLayer`. Six events exist; adding a seventh is
  a five-step process documented in [docs/analytics.md](../docs/analytics.md).
- GTM loads only when `GATSBY_GTM_ID` is set. It is unset here.

## SEO

`src/components/seo/Seo.tsx` is the only component that emits a meta tag. Every
page's `Head` export renders exactly one of it and passes `pathname`, which is
required so a page cannot ship without a canonical.

- `src/lib/seo/urls.ts` builds absolute URLs, and omits them entirely when no
  origin is configured rather than emitting a localhost canonical.
- `src/lib/seo/structured-data.ts` builds one JSON-LD `@graph` per page:
  Organization and WebSite everywhere, Article and BreadcrumbList on resource
  pages.
- `src/lib/seo/robots.ts`, `og-image.ts` and `favicon.ts` are pure builders;
  `gatsby-node.ts` writes their output into `public/` at the end of the build.
- The sitemap comes from `gatsby-plugin-sitemap`, generated from the pages
  Gatsby actually built.

## Styling

CSS Modules plus design tokens as CSS custom properties.

- `src/styles/tokens.css` — primitives (`--nh-slate-500`) and semantic tokens
  (`--nh-color-text`). **Components use semantic tokens only.**
- `src/styles/global.css` — reset and base element styling.
- `src/styles/fonts.css` — the two font subsets the site actually renders.
- Everything else is a `*.module.css` beside its component.

Contrast is asserted against the token file in `src/styles/contrast.test.ts`, so
lowering a colour fails CI with the measured ratio.

## Testing

Jest with jsdom, Testing Library, and `jest-axe` wired into `expect`.

- Tests sit beside the code they cover.
- Query by role and accessible name; mock at the network boundary (`fetch`), not
  the module boundary.
- `__mocks__/gatsby.tsx` renders `Link` as a real anchor so navigation and axe
  assertions mean something.
- CSS-level invariants (contrast, reduced motion, reflow, focus) are asserted by
  parsing the stylesheets, because jsdom applies no CSS.
- `project.test.ts` asserts repository-level contracts: Node version
  consistency, the CI gates, workflow permissions, sitemap configuration.

## CI

`.github/workflows/ci.yml`, on pull requests and pushes to `main`:

```
npm ci → lint → format:check → typecheck → test → build
```

`contents: read`, no secrets, first-party actions only, Node from `.nvmrc`. It
validates; it does not deploy. Nothing is deployed anywhere yet.
